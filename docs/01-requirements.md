# 需求与成功标准

## 1. 文档状态与依据

用户已选择第 1 题，并确认 LangGraph、百炼模型及主要业务口径。本文件依据题目、考核规则和用户确认。具体确认边界见 `06-decisions.md`。开发者不得把待确认建议当成既定需求。

## 2. 用户与目标

运营人员输入活动主题、预算和截止时间。系统使用合成素材和工具费用、耗时表，生成并保存可行的内容活动方案。系统在无法完成时说明原因和缺口。

## 3. 考核硬要求

| 编号 | 系统要求 | 验证方式 |
| --- | --- | --- |
| R01 | 系统接收主题、预算、截止时间，使用合成素材和费用、耗时表。 | 输入校验与数据检查。 |
| R02 | 系统提供素材检索、脚本生成、成本估算、方案保存四类工具。 | 工具测试与实际调用记录。 |
| R03 | 系统输出计划、步骤状态、工具结果、费用合计，以及保存结果或未完成原因。 | 输出字段和保存产物核对。 |
| R04 | 模型观察工具结果后，选择下一步动作、替代方案或停止。 | 至少两条不同路径的真实模型记录。 |
| R05 | 系统处理费用超限、工具错误和部分成功，并保留成功结果。 | 故障注入与状态断言。 |
| R06 | 系统覆盖正常完成、缺预算、缺截止时间、工具失败、预算超限、重复执行。 | 全部必测场景。 |
| R07 | 系统设定执行步数或工具调用上限，并在超限时明确返回未完成。 | 上限测试。 |
| R08 | 项目提供可复制的运行步骤、可执行测试和完整交付材料。 | 干净环境复跑和交付检查。 |
| R09 | 验证材料至少包含三组实际输入、输出和记录，并覆盖所有验收点。 | examples 文件与评估文档逐项对应。 |

失败步骤续跑属于题目加分项。开发者不能用它替代重复执行的必测要求。

## 4. 已确认的首版范围

系统只处理单个用户、单个活动和串行任务。系统使用本地合成数据和本地业务工具。真实模型负责动作选择，业务工具可采用 Mock。

首版暂不包括真实素材平台、支付、真实发布、多人并发、界面、线上部署和多 Agent。这个范围是开发建议，不是额外考核限制。

## 5. 输入与输出设计

输入包括 `request_id`、`theme`、`budget` 和带时区的 `deadline`。测试场景单独传入固定起点和故障配置，普通业务输入不承担故障控制职责。

输出包括任务状态、计划版本、步骤及依赖、素材和脚本结果、费用明细、时间估算、保存凭据、未完成原因和待补信息。输出应提供便于测试的结构化形式。

当预算或截止时间缺失时，系统说明缺失字段并等待补充。系统不能自行编造用户约束。负预算、非法时间和已经过去的截止时间也需要明确处理。

## 6. 成功标准

只有当方案内容完整、当前方案通过费用与时间检查、保存工具确认成功且存在可读取产物时，系统才能报告完成。

系统必须区分方案预计费用、已经发生的费用和模型 API 用量。系统不能把不可行方案的估算值直接记为已发生费用。

当系统不能完成时，系统必须给出真实终态、已成功结果、失败步骤和可计算的费用或时间缺口。系统不能把工具失败写成成功。

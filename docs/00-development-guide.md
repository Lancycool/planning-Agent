# 后续开发指导

## 1. 当前阶段

项目已经选定第 1 题。用户已确认技术栈、百炼模型、接入 Host 和本轮提出的全部业务规则。P1—P4 和 P5 本地交付材料已经完成，远程仓库尚未创建。实际阶段记录见 `examples/development-log.json`。

开发者应先阅读 `06-decisions.md`。P0 的方案确认已经完成；后续开发按 P1—P5 推进。真实密钥配置和联通验证不能用方案确认代替。

## 2. 开发顺序与阶段检查

| 阶段 | 开发者需要完成的工作 | 阶段结束条件 |
| --- | --- | --- |
| P0：确认方案 | 开发者确认技术栈、模型、预算、时间、重复执行、存储和范围。 | 决策文件有明确确认记录。 |
| P1：固定规则与数据 | 开发者定义输入输出、任务状态、工具契约、费用事件和合成场景。 | 场景能够人工算清费用与时间；规则没有相互矛盾。 |
| P2：完成工具与状态 | 开发者实现四类工具、状态存储、防重复保存和故障注入。 | 工具测试通过；保存结果可读取；费用与结果保留可核对。 |
| P3：接入模型循环 | 开发者用 LangGraph 实现状态、节点和条件边，并接入百炼模型、动作校验、反馈、终态核验和调用上限。 | 真实模型能够运行核心链路；离线模式有明确标记；固定分支不代替模型决策。 |
| P4：验证异常与决策 | 开发者运行必测场景及关键边界，并保留实际 Trace。 | 全部必测项有证据；至少两条路径体现真实模型调整动作。 |
| P5：完成交付 | 开发者补齐运行步骤、依赖、环境示例、评估、AI 使用记录和复盘。 | 项目可复跑；材料一致；测试结果真实；提交地址和 SHA 明确。 |

开发者可以使用离线模型替身验证 P2 和执行程序，但不能据此把 P3、P4 的真实模型要求标为完成。

## 3. 时间安排

考核建议投入三小时。建议把规则和数据整理控制在约 20 分钟，把工具、状态和模型循环控制在约 85 分钟，把测试与真实运行控制在约 45 分钟，把文档、复跑和交付控制在约 30 分钟。

这个安排只用于分配精力，不代表完成时间承诺。开发者需要记录已经发生的文档整理时间。模型接入、环境或测试出现阻碍时，开发者应说明影响，并与用户确认范围调整。

## 4. 开发优先级

开发者首先保证正常完成、缺字段、工具失败、预算调整和重复执行。开发者同时保证调用上限和可信终态，因为这些要求影响整个运行流程。

开发者接着整理真实模型证据和可复跑材料。开发者只有在必测项稳定后，才安排失败续跑等加分项。用户未确认的新增功能不能直接进入开发。

## 5. 计划交付结构

```text
README.md
src/                  # 业务代码、模型接入、工具、状态与 Trace
tests/                # 可执行测试
data/                 # 合成素材、费用与耗时规则
examples/             # 实际输入、输出、Trace 和测试报告
docs/                 # 本组指导与交付文档
依赖文件               # 技术栈确认后选择
.env.example          # 模型配置说明，不含真实密钥
.gitignore            # 排除密钥、本地运行状态等不宜提交内容
```

上述代码、测试、合成数据和证据目录现已建立。项目使用 `pyproject.toml` 与 `uv.lock` 管理依赖，`env.sample` 和 `.env.example` 提供本地配置模板。开发者不得把未完成的远程交付或续跑能力写成已实现。

## 6. 完成检查

- 开发者核对全部需求编号与验收场景。
- 开发者核对费用明细、时间计算、步骤依赖和实际保存产物。
- 开发者检查至少三组实际验证材料和至少两条真实模型路径。
- 开发者检查在线与离线模式标记，以及调用上限的未完成输出。
- 开发者在干净环境按 README 复跑安装、运行和测试步骤。
- 开发者检查秘密信息、依赖版本、实际用时、失败和已知限制。
- 开发者在交付时核对题号、GitHub URL、最终 SHA 和访问权限。

开发者在用户明确要求或确认后处理仓库创建、公开范围和推送目标。当前阶段不创建远程仓库，也不生成虚假的提交信息。
